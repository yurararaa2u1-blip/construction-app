1. プロジェクト概要

1-1. 一言でいうと

建築工事現場の「進捗管理」と「遅延通知」をブラウザとメールでできるWebアプリです。

1-2. 課題（なぜ作ったか）

建築工事の現場では、以下のような課題があります。

  • 進捗が現場ごとにバラバラ管理：紙、Excel、ホワイトボードなど属人的
  • 遅延の発見が遅い：気付いた時には手遅れ
  • 情報共有が非効率：管理者と現場監督の間で情報が伝わりにくい

このアプリはこの3つを「ブラウザで一元管理し、遅延を自動検知してメール通知する」ことで解決します。

1-3. ターゲットユーザー

以下の3つの役割（ロール）を想定して設計しました。

ロール実際の職種イメージできること
管理者（admin）建築会社の管理職全機能（現場・工程・メンバー・ユーザー管理）
現場監督（supervisor）現場の責任者現場閲覧、担当工程の進捗更新
閲覧のみ（viewer）クライアント・関係者閲覧のみ、更新不可

1-4. 主な特徴

  • 📱 スマホ・PCどちらでも使える（レスポンシブ対応）
  • 🔒 JWT認証でセキュアなログイン
  • 📧 遅延タスクを自動検知してメール通知（AWS SES）
  • ⚙️ 役割ごとに画面と機能が変わる（RBAC / 権限制御）
  • 🌐 AWSクラウドで本番稼働中（EC2 + RDS + S3 + CloudFront）

3-2. データフロー例：ユーザーが進捗を更新する時

  1. ユーザーがブラウザで進捗率を50→75%に変更
  2. Reactが PATCH /api/tasks/:id をJWT付きで送信
  3. CloudFront → EC2 の Express にリクエストが到達
  4. 認証ミドルウェアがJWTを検証
  5. 権限チェック（admin または supervisor か？）
  6. コントローラーが RDS の tasks テーブルを UPDATE
  7. is_delayed を再計算（期限切れ？進捗100%未満？）
  8. 更新結果をJSONで返す
  9. Reactが画面のプログレスバーを更新

3-3. データベース設計

5つのテーブルで構成されています。

テーブル主なカラム役割
usersid, name, email, password_hash, role, deleted_atユーザー情報
projectsid, name, address, start_date, end_date, status, created_by, deleted_at現場情報
project_membersproject_id, user_id, role, joined_at現場のメンバー
tasksid, project_id, name, planned_end, progress, is_delayed, assigned_to工程
notificationsid, user_id, project_id, task_id, type, message, is_read通知履歴
設計上のこだわり：
  • 主キーは全て UUID（連番IDより推測されにくく、分散環境で衝突しない）
  • 削除は 論理削除（deleted_at にタイムスタンプ）で復元可能
  • パスワードは bcrypt でハッシュ化（password_hashに保存、平文は不可）

4. 使用した技術スタックと説明

初学者にもわかるように、「これは何？」「なぜ選んだ？」「今回どう使った？」 の3点で説明します。

4-1. フロントエンド

🎨 React

これは何？：Facebook（現Meta）が開発した、ユーザーインターフェース構築のためのJavaScriptライブラリ。世界で最も使われているフロントエンド技術の1つ。「コンポーネント」という部品を組み合わせて画面を作る。

なぜ選んだ？：圧倒的なシェアで情報量が多い、求人でも需要が高い、Meta・Netflix・Airbnbなど大手が採用。

今回どう使った？：8つの画面すべてをReactで構築。useStateで入力フォームの値管理、useEffectでデータ取得タイミングを制御、react-router-domで画面遷移。

JavaScriptComponentHooksSPA

🎨 Tailwind CSS + カスタムCSS

これは何？：「クラス名を指定するだけでスタイルが当たる」CSSフレームワーク。例：<button class="bg-blue-500 text-white px-4 py-2">。

なぜ選んだ？：素早く見栄えの良いUIが作れる、ダークテーマ・レスポンシブが容易、業界で標準化してきている。

今回どう使った？：コーポレート系のカラースキーム統一、スマホ・PC対応（768px幅で切り替え）、ハンバーガーメニュー実装。

CSSResponsive

4-2. バックエンド

🟢 Node.js + Express

これは何？：Node.jsはJavaScriptをサーバー側で動かす実行環境。ExpressはNode.jsで最も使われるWebフレームワーク。リクエストを受け取ってレスポンスを返す仕組みを提供。

なぜ選んだ？：フロントとバックが同じ言語（JavaScript）で書ける、起動が速く非同期処理が得意、npmで豊富なライブラリが使える。

今回どう使った？：REST APIを16個実装（認証・現場・工程・メンバー・通知など）、ミドルウェアで認証チェックを共通化、ルーティングをファイル分割して保守性向上。

JavaScriptREST APIMiddleware

🔒 JWT（JSON Web Token）

これは何？：「あなたは誰か」を証明する電子的な札のようなもの。サーバーで発行され、クライアントは以降のAPIリクエストにこれを添えて送る。

なぜ選んだ？：サーバー側で状態を持たなくてよい（ステートレス）、複数サーバーに分散しても動く、モダンなアプリの標準的な認証方式。

今回どう使った？：ログイン成功時にJWTを発行（有効期限24時間）、フロント側はlocalStorageに保存、全APIリクエストのヘッダーに付ける、期限切れは自動でログイン画面へリダイレクト。

AuthenticationStateless

🔐 bcrypt

これは何？：パスワードを安全に保存するためのハッシュ化ライブラリ。パスワードから「元に戻せない文字列」を生成する。「わざと遅い」設計になっており、総当たり攻撃に強い。

なぜ選んだ？：パスワードは絶対に平文で保存してはいけない。bcryptはセキュリティ業界のデファクトスタンダード。

今回どう使った？：登録時に入力パスワードをbcryptでハッシュ化してDBに保存、ログイン時に入力パスワードのハッシュとDBの値を比較。

SecurityHash

4-3. データベース

🗄 PostgreSQL

これは何？：世界で最も高機能なオープンソースのリレーショナルデータベース。SQLでデータを操作。Amazon・Instagram・Redditなど大規模サービスでも採用。

なぜ選んだ？：無料で使える、高機能（トランザクション・外部キー・インデックスなど本格機能が全て使える）、JSONBデータ型で柔軟なデータも扱える、AWS RDSで本番運用しやすい。

今回どう使った？：5テーブル設計、外部キー制約でデータ整合性を保証、UUID主キーで安全性向上、論理削除パターンでデータ復元可能。

RDBMSSQLOpen Source

6. 苦労したこと・解決方法・工夫点

このセクションは面接での「困った経験を教えてください」という質問への準備でもあります。

6-1. Mixed Content問題

問題：CloudFront経由でフロント（HTTPS）を配信していたが、バックエンドEC2はhttp://でしか動かない。ブラウザが「HTTPSページからhttp://のAPIを叩くのはブロックする」と拒否。

原因の理解：Mixed Content（混在コンテンツ）といい、ブラウザのセキュリティ機能。HTTPSページに読み込まれる内容は全てHTTPSでなければならない。

解決策：CloudFrontをAPI用にもう1つ作成（d2sqygsot7k84c.cloudfront.net）。CloudFrontが受けたHTTPSリクエストをEC2のHTTPに変換。結果：ブラウザはHTTPSしか使わないのでMixed Content解消。

学んだこと：HTTPSの本質的な意味、CDNは「速く配信」だけでなく「HTTPSラッパー」としても使える、インフラを抽象的な絵で描けるようになった。

6-2. IAMアクセスキーの漏洩とローテーション

問題：動作確認のためスクリーンショットをClaude共有したが、その中にAWSアクセスキーが写り込んだ。チャットログにキーが残ってしまった。
気づいた瞬間の対応：
  1. キーが漏れた前提で即座に無効化・新規発行を実施
  2. 全ての参照箇所（ローカル.env、EC2 .env）を新キーに書き換え
  3. 疎通テストして新キーで動作することを確認
  4. 古いキーを削除して漏洩キーを無効化

学んだこと：セキュリティは「事後対応の速さ」も重要、スクリーンショット共有時は機密情報を確認する習慣、キーローテーションはいざという時のための訓練、本番運用ではIAMロール（キー不要）を使うべき。

6-3. EC2再起動でIPが変わる問題

問題：AWSクレジット節約のため作業終了時にEC2を停止していたが、再起動時にパブリックIPが変わる → CloudFrontのオリジンを毎回手動更新。手間もミスも多かった。
解決策：Elastic IPを導入して固定IPを取得。一度だけCloudFrontのオリジンを更新すれば以降変更不要。コスト増：停止中でも月$3.60（許容範囲）。

学んだこと：インフラの「運用のしやすさ」もコストの一部、トレードオフを数字で判断する感覚、何度も繰り返す作業は自動化・固定化するべき。

6-4. デプロイの落とし穴：git pullが黙って失敗していた

問題：修正コードを本番反映したが動作しない。キャッシュクリアもした。実はEC2側のgit pullが認証エラーで失敗していたのに気付いていなかった。

症状：git pullコマンドは実行したがPAT入力を間違えていた。「Authentication failed」で終了したが、そのままPM2 restartもしていた。結果：古いコードのまま動いていた。

解決策：反映後は必ず git log --oneline で最新コミットを確認する習慣にした。コード変更が反映されているかは grep で確認する。

学んだこと：「コマンドを打つ」と「効果が出る」は別という当たり前を痛感。サイレント失敗はエンジニアの敵。確認・検証まで含めて「デプロイ完了」と定義するべき。

6-5. 未実装バグの発見

問題：手動テスト計画に沿って検証を進めていたら、「パスワード短さでエラー」「日付逆順でエラー」の項目が未実装だと判明。設計書にはあるが実装漏れていた。
対応：テスト計画上「未実装バグ」として明確に記録、発見当日にバックエンド＋フロントエンドの両方に実装、本番反映＆再検証まで完了。

学んだこと：設計と実装のギャップは必ず生まれる → 体系的なテストが重要。「動く」と「仕様通り」は違う。テスト工程は品質保証だけでなく 仕様通りかの検証 でもある。

6-6. AWSコスト意識

問題：AWS学習用に無料クレジット$140が付与されたが、そのままだと月$25消費で5-6ヶ月で枯渇。学習期間中は節約したかった。
工夫：作業終了時にEC2・RDSを停止する運用ポリシーを確立、「同日中に再開なら停止しない」など判断基準を作成、Elastic IPは「使いやすさと費用のトレードオフ」で判断、定期的にコストを確認する習慣。

結果：月$1未満で運用できている。クレジット消費を最小化して開発期間を延長。

学んだこと：クラウドは使い方次第で費用が大きく変わる、コスト最適化は「単に安くする」ではなく「トレードオフを理解して選ぶ」、実務でも重要になる感覚。
